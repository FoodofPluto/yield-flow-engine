# Controlled closed-beta invitations (Prompt 19C.1)

Public signup stays disabled in Render and hosted Supabase. A trusted operator may issue one email-free invitation with `python scripts/manage_beta_invites.py create --actor-user-id <verified-admin-uuid>` in the existing protected shell. It prints a non-sensitive invitation ID and the URL once. Forward the URL privately; do not paste it in operational records, tickets, logs, analytics, or screenshots. No file output, bulk issuance, public creation endpoint, email collection or entitlement grant is added. Revoke an unused/claimed invitation with the same command's `revoke --invitation-id <uuid>` option. Only a service-role caller naming an existing verified administrator can issue/revoke. The CLI follows the established manage_accounts.py trust boundary: possession of that backend credential is privileged, and the actor parameter is never accepted from the browser.

Invitations contain 256 bits from Python secrets and expire after 24 hours. Only SHA-256 digests are persisted in private.beta_invitations. There are no client table grants or RLS policies. Public RPCs are service-role-only, also check the JWT role, and have an empty search_path. Operator issue/revoke records retain timestamps and actor identity without participant email or bearer secrets.

## Lifecycle and canonical admission

The broker handles exactly /create-account?invite=<opaque-token>, validates on the server, puts the bearer in a temporary Secure/HttpOnly/SameSite=Lax host cookie and immediately replaces browser history/location with a token-free Account landing. The body contains no bearer. Invalid, expired, claimed, revoked and consumed entries all show the same participant-safe unavailable state. The main-page form uses the existing FuruFlow visual system and its existing email/password verification flow.

Streamlit calls a bridge-key-protected loopback endpoint. The broker atomically claims an unused invitation with one conditional PostgreSQL UPDATE, reserving one generated UUID. The claim cannot be released/retried, including after timeouts. Supabase's trusted admin create-user API receives that UUID, participant-entered email/password and email_confirm=false; it receives no invitation secret/digest/metadata and never updates an existing account. An AFTER INSERT trigger consumes the reservation and writes canonical beta admission within the SAME Auth transaction. Expired/revoked/older-than-five-minute claims abort the insert. Replay cannot create a second admitted identity. Provider failures may burn an invitation; fail closed and issue a new one after investigation rather than reopening it.

The canonical private.beta_admission snapshot gains invited_user_ids, written only by this transaction. Its existing environment synchronization leaves that column intact. The existing private.alert_beta_admitted predicate still requires a verified, undeleted Auth user and entitlement record; all account reconstruction continues to use that predicate. Admission no longer consults the invitation after consumption. No Pro/demo/paid grants change; Alerts' paid and trusted-Telegram requirements are unchanged. The invitation cookie is cleared through the broker after successful creation and cannot authorize further accounts even if cookie clearing is interrupted.

After creation the existing resend_verification initiates the accepted PKCE flow. The participant follows the verification email, and the existing callback, identity reconstruction, activation ticket, opaque session cookie, refresh rotation, recovery and global sign-out mechanisms remain authoritative. No new redirect origin, wildcard, implicit-token callback or email auto-confirm is added. If email request fails, the account remains unconfirmed and the participant can request verification again; do not claim delivery from request success. Existing sign-in/recovery remain available.

## Threat model and limits

- Link theft: this is a bearer invitation. Anyone holding it before use may redeem it. A short TTL, private forwarding and operator revocation reduce exposure; the system cannot identify the intended recipient without collecting an identity first.
- Guessing/abuse: 256-bit entropy, strict fixed syntax, Nginx 10 entry requests/minute per proxy-visible address (burst 5), plus 60 validation/redemption operations/minute per broker process. The current broker uses one process. Limits may group clients behind Render/NAT; do not trust arbitrary forwarded IP headers. Restart resets the in-memory budget, but never database consumption. Distributed rate limits would require review if the broker is scaled.
- Replay/races: conditional UPDATE plus unique reserved UUID; claim is terminal and consumption/admission occurs in the Auth insertion transaction. Revocation locks/updates the same row. Ambiguous failures are not retried.
- URL/referrer/log exposure: initial bearer navigation is unavoidable. Subsequent navigation is token-free, no-referrer/no-store, no external resources, no token in HTML, Nginx invitation access/error logging disabled, and broker query log filter redacts after interpolation. HttpOnly prevents page-script cookie reads. Render/edge/browser initial-navigation retention is not represented as absent; review actual production logs with safe match counts after authorized redemption, never copy the secret into the report.
- CSRF/open redirects: GET only captures an invitation; it does not create an account. Registration is through the existing Streamlit XSRF/WebSocket boundary and private bridge. No browser-selected redirects, owner IDs, entitlement fields or metadata are accepted. Public /v1/invitations* is denied by Nginx.
- Partial creation: account + admission + consumption are transactional. Confirmation/email delivery is necessarily an external subsequent operation; failure leaves an unverified account, not authenticated beta access. Never release an ambiguous claim or auto-confirm to repair delivery.
- Operator misuse: service-role secrets remain broker-only; verified admin actor checks and private lifecycle state support review. Existing trusted backend access can administer Supabase and is not made safe against a compromised operator by this feature.
